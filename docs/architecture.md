# FlowLens Architecture

This document describes the architecture of FlowLens as of the foundation
phase. It focuses on what exists today and the seams that later phases build
on.

## System context

FlowLens has three runtime components and depends on the GitHub API.

```
            ┌──────────────┐         ┌──────────────┐        ┌──────────────┐
  Browser ──▶  Next.js web │──REST──▶│    Go API    │──SQL──▶│  PostgreSQL  │
            └──────┬───────┘         └──────┬───────┘        └──────────────┘
                   │                        │
                   │  OAuth redirect        │  GitHub REST
                   ▼                        ▼
            ┌───────────────────────────────────────┐
            │               GitHub                   │
            └───────────────────────────────────────┘
```

- **Actors:** engineering managers, tech leads, and developers who want to
  measure their PR flow.
- **External systems:** GitHub (OAuth + REST API). Azure services (Container
  Apps, PostgreSQL, Service Bus, Key Vault, Application Insights) are future
  deployment targets.

## Main components

### Web (`apps/web`)

Next.js App Router application. React Server Components are the default;
Client Components are used only where interactivity is required (e.g. the
logout button). A thin server-side API client (`lib/api.ts`) calls the Go
API and forwards the session cookie. Client-safe config lives in
`lib/config.ts` so client components never import server-only modules.

### API (`apps/api`)

Go REST API with clearly separated responsibilities, kept intentionally
lightweight (no heavy Clean Architecture layering yet):

- `internal/http` — HTTP handlers, routing (chi), middleware (CORS, request
  logging, auth), cookie management, and response helpers.
- `internal/auth` — token cipher (interface + AES-GCM impl), session
  service, and OAuth config/state helpers.
- `internal/user` — user domain model and the service that upserts users.
- `internal/github` — the GitHub client interface, its HTTP implementation,
  and a fake for tests.
- `internal/database` — the pgx connection pool and the sqlc-generated
  query code (`internal/database/db`).
- `internal/config` — environment configuration loading and validation.
- `cmd/api` — the entry point (wiring, graceful shutdown).

### Database

PostgreSQL. The schema is owned by `golang-migrate` migrations in
`apps/api/migrations`. Type-safe query code is generated by sqlc from the
`.up.sql` schema plus hand-written queries in
`internal/database/queries`.

## Request flow

A typical authenticated request:

1. The browser requests a page from Next.js (e.g. `/dashboard`).
2. The Server Component calls `getCurrentUser()`, which fetches
   `GET /api/v1/me` from the API, forwarding the browser's session cookie.
3. The API's `requireAuth` middleware hashes the cookie token, looks up the
   session (joined to the user), and puts the user in the request context.
4. The handler returns the user as JSON; the page renders or redirects to
   `/login` when unauthenticated.

## Authentication flow

FlowLens uses GitHub OAuth with **server-side sessions**.

```
Browser                Go API                       GitHub
  │  GET /auth/github     │                            │
  ├──────────────────────▶│  set state cookie          │
  │                       ├── 307 redirect ───────────▶│
  │                       │                            │  (user authorizes)
  │  GET /auth/github/callback?code&state              │
  │◀──────────────────────┤◀───────────────────────────┤
  │                       │  verify state cookie       │
  │                       │  exchange code → token     │
  │                       ├── GET /user ──────────────▶│
  │                       │  upsert user (token encrypted)
  │                       │  create session
  │◀── 307 + session cookie│                            │
  │  GET /dashboard        │                            │
```

Key properties:

- **State parameter** in a short-lived HttpOnly cookie defends the OAuth
  flow against CSRF; it is compared in constant time.
- **Sessions are opaque and server-side.** The cookie holds a random token;
  only its SHA-256 hash is stored, so a database leak does not yield usable
  tokens. Sessions can be revoked (logout) and expire server-side.
- **Access tokens are never stored in plaintext.** They are encrypted with
  the `TokenCipher` before persistence.
- **The cookie is HttpOnly**, so the access/session token is never exposed
  to JavaScript or `localStorage`. `Secure` is enabled in production.

## GitHub synchronization flow

Not implemented yet, but the design is fixed by the current seams:

- The `github.Client` interface is the single place all GitHub calls go
  through. Pagination, rate-limit handling, retries, and timeouts will live
  behind it, and the `FakeClient` lets sync logic be tested without network.
- PR sync will be **idempotent**: rows are upserted by
  `github_pull_request_id`, so re-running a sync (or a duplicate webhook
  delivery) converges to the same state. `sync_runs` records each run.

## Database overview

Current tables (created in the initial migration so the foundation is
complete):

- `users`, `sessions` — used today for auth.
- `organizations`, `organization_members`, `repositories`,
  `pull_requests`, `pull_request_reviewers`, `sync_runs` — created now,
  populated in later phases.

Design notes:

- UUID primary keys (`gen_random_uuid()`), `timestamptz` everywhere.
- Natural GitHub IDs (`github_user_id`, `github_repository_id`,
  `github_pull_request_id`) carry `UNIQUE` constraints to make upserts safe.
- Foreign keys cascade on delete so removing a repository cleans up its PRs.

## Security considerations

- Secrets come only from the environment / `.env` (git-ignored); nothing is
  hard-coded. Production will source them from Azure Key Vault.
- Token encryption is behind an interface so the crypto backend can change
  without touching callers.
- CORS allows only the configured web origin and enables credentials.
- CSRF: the OAuth flow uses the state parameter; API mutations currently
  rely on `SameSite=Lax` cookies plus the locked CORS origin, with a
  double-submit token planned.
- The production Docker image runs the API as a non-root user from a static
  binary.

## Main trade-offs

- **Server-side sessions vs JWT:** sessions add a database lookup per
  request but give instant revocation and keep no secret material in the
  cookie. For an internal analytics tool this is the safer default.
- **sqlc vs ORM:** sqlc gives type-safe SQL without hiding the queries,
  matching the "avoid over-abstraction" goal, at the cost of a code-gen
  step.
- **All tables created up front vs incremental migrations:** creating the
  full schema now keeps the foundation coherent, at the cost of having
  tables with no code behind them yet.
- **Monorepo:** one repo simplifies local development and shared docs at the
  cost of mixing Go and Node toolchains in one tree.
